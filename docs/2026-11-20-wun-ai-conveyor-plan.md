## 0. Короткий вывод

1. **Идея рабочая, сроки и цены в тексте — нет.** «За 7 дней развернуть, за 90 дней доход» — это не про видео-инференс и не про нашу платформу. Реальный пилот одного ролика — 2–3 недели, и он стоит десятки долларов на GPU, а не «бесплатно».
2. **В тексте есть фактические ошибки**, на которых нельзя строить закупку железа (раздел 1). Главная: «OpenCineAgent, 14 агентов, открытая лицензия» — проект с таким названием существует, но это 130 КБ без лицензии и без развития (см. `2026-11-20-wun-ai-conveyor-research-ru.md`). «Ядро» из него не получится — собирать придётся самим.
3. **У нас в репозитории нет ни одной строки производства медиа.** `src/lib/media/` — это вложения к постам и waveform. Значит конвейер — новый модуль, а не доработка существующего.
4. **Правильный первый шаг** — не Лувр, не ТВ, не музыка, а **один рекламный ролик 30 секунд** от брифа до готового файла, с одним человеком на приёмке. Это же рекомендует и сам автор текста в последнем сообщении.
5. **Платформенная часть** (то, что реально делается в этом репозитории) — очередь задач, стадии, артефакты, приёмка, публикация, биллинг. Модели живут снаружи, за адаптерами.

## 2. Что из этого уже есть в WUN

Проверено по репозиторию на 2026-11-20:

- **Веб**: React 18 + Vite + Tailwind + shadcn, страницы в `src/pages/` (есть `AdsDashboard`, `Market`, `Live`, админка).
- **Supabase**: Auth, Postgres, Storage. Edge-функции, которые пригодятся: `ai-moderation`, `companion`, `adk-civic`, `wun-bot-scheduler`, `send-email`, `send-welcome`, `rate-limit`.
- **Блокчейн**: `blockchain/` (Node, свой узел), якорение (`wun-anchoring`, `twun-chain-anchor`).
- **Мобайл**: `flutter_app/`, **Orbita**: Godot (`godot/orbita/`).
- **Биллинг**: `docs/PASSPORT_BILLING.md`, кошелёк и тарифы уже описаны.
- **Чего нет**: очереди задач, реестра моделей, стадий производства, артефактов, приёмки контента, публикации в ТВ/Лувр. Ни одного файла.

Отсюда важный вывод по приоритетам: **80% работы — это платформа (очередь, стадии, артефакты, приёмка, деньги), 20% — сами модели.** Модели можно менять каждые полгода, платформа останется.

## 3. Целевая архитектура (5 частей)

```
brief ──▶ [1] Orchestrator ──▶ [2] Stage workers ──▶ [3] Model adapters
                   │                    │                      │
                   │                    ▼                      ▼
                   │            [4] Artifact store (Storage)
                   │                    │
                   └──▶ [5] Human gate ─┴──▶ publish (TV / Louvre / Market) ──▶ billing
```

1. **Orchestrator** — Postgres-таблица заданий + edge-функция-диспетчер по cron. Не «агент», а очередь с состояниями: `queued → running → failed/succeeded → approved/rejected`. Ретраи, таймауты, лимит бюджета на задание.
2. **Stage workers** — по одному воркеру на стадию, каждый идемпотентный, каждый берёт лейз на строку (`FOR UPDATE SKIP LOCKED`).
3. **Model adapters** — единый интерфейс `VideoProvider`, `ImageProvider`, `TtsProvider`, `MusicProvider`, `LlmProvider`. За ним: свой ComfyUI на арендованном GPU, Replicate/fal, или API. Смена провайдера = смена одного файла, не переписывание пайплайна.
4. **Artifact store** — Supabase Storage + таблица метаданных: версия, стадия, промпт, модель, стоимость, длительность. Без этого нельзя ни сравнить две генерации, ни посчитать себестоимость.
5. **Human gate + publish** — экран приёмки (превью, approve/reject, комментарий), затем публикация в WUN-TV / Лувр / маркет и списание с кошелька.

Стадии пилота (6): `script` → `storyboard` → `shots` → `audio` → `assembly` → `qc`. Дальше `approval` → `publish`.

**Про «24/7 и петлю».** Петля — это не автономный агент с мышкой, а: расписание (cron) + входящие события (новый экспонат, новый пост) + очередь + бюджетные лимиты + алерты. Агент с computer use добавляем последним и только на монтажную вёрстку, если ffmpeg-шаблонов не хватит.

## 4. Данные (предлагаемая схема)

DDL — **только через Supabase MCP** (`apply_migration`), по правилу репозитория. Ниже — намерение, не готовый SQL.

| Таблица           | Зачем                     | Ключевые поля                                                                        |
| ----------------- | ------------------------- | ------------------------------------------------------------------------------------ |
| `ai_briefs`       | что заказываем            | id, owner_id, kind (ad/film/guide), topic, tone, duration_s, language, status        |
| `ai_jobs`         | одно задание = один ролик | id, brief_id, state, budget_usd, spent_usd, attempts, error, created_at              |
| `ai_job_steps`    | стадии задания            | id, job_id, stage, state, provider, model, locked_until, payload jsonb               |
| `ai_artifacts`    | результат стадии          | id, step_id, kind (text/image/video/audio/final), storage_path, meta jsonb, cost_usd |
| `ai_models`       | реестр моделей и цен      | id, name, kind, provider, license, price_per_unit, enabled                           |
| `ai_publications` | куда опубликовали         | id, artifact_id, channel (tv/louvre/market), external_id, published_at               |
| `ai_costs`        | сводка расходов           | day, job_id, provider, usd                                                           |

RLS: пользователь видит свои `ai_briefs`/`ai_jobs`, админ — всё. Публикация в ТВ — только через серверную роль.

## 5. Что писать в репозитории

**Общий код** — `src/lib/ai/conveyor/`:

- `types.ts` — `Stage`, `JobState`, `Artifact`, `Brief`;
- `machine.ts` — переходы состояний и правила ретраев (чистая функция, покрывается Vitest);
- `providers/` — по файлу на провайдера плюс `mock.ts` (мок, чтобы весь пайплайн гонялся без денег);
- `cost.ts` — расчёт стоимости по прайсу из `ai_models`.

**Edge-функции**:

- `ai-conveyor-dispatch` — берёт созревшие задания/шаги, ставит в работу, соблюдает бюджет;
- `ai-conveyor-step` — выполняет одну стадию одного шага (идемпотентно, с лейзом);
- `ai-conveyor-webhook` — колбэки провайдеров (видео генерируется минутами, синхронно нельзя);
- `ai-conveyor-publish` — приёмка → публикация → списание.

**UI**:

- `/studio` — список проектов и их стадий;
- `/studio/:id` — таймлайн стадий, превью артефактов, кнопка approve, стоимость на экране;
- всё под фича-флагом, в прод до пилота не включаем.

**Порядок работ (первый срез, ~3–4 дня инженера):**

1. Таблицы + RLS (через MCP).
2. `types.ts` + `machine.ts` + тесты на переходы.
3. `mock.ts` + сквозной прогон брифа до «готового» файла-заглушки.
4. `/studio` MVP: список, карточка, approve.
5. Один реальный провайдер (изображения — самый дешёвый шаг для проверки).

После этого добавление видео — это новый адаптер и новая стадия, а не новый проект.

## 6. Пилот: один рекламный ролик

**Скоуп:** 30 секунд, 1080p, 6 шотов, русская озвучка, музыка, титры. Один бренд (можно WUN).

**Что автоматизируем полностью:** сценарий, раскадровку, промпты, генерацию шотов, озвучку, музыку, сборку, субтитры, QC по формальным критериям (длина, разрешение, громкость, наличие лица в кадре).

**Где человек:** выбор лучшего из 2–3 вариантов сценария, приёмка визуала (артефакты AI-видео всё ещё ломают руки и текст), финальный approve.

**Оценка себестоимости одного ролика** (при аренде GPU ~$1.5–3/час):

| Статья                  | Расчёт                       | Итого                                           |
| ----------------------- | ---------------------------- | ----------------------------------------------- |
| Видео-шоты              | 6 шотов × 3 попытки × ~4 мин | ~72 мин GPU → $2–4                              |
| Изображения/раскадровка | 12 картинок                  | $1–2                                            |
| Озвучка                 | 30 c, TTS                    | $0.5–1                                          |
| Музыка                  | 30 c                         | $0.5–1                                          |
| LLM (сценарий, QC)      | ~50 запросов                 | $1–2                                            |
| Монтаж                  | ffmpeg локально              | $0                                              |
| **Итого**               |                              | **$5–10 за ролик** (без учёта времени инженера) |

**Критерии успеха пилота:** бриф → готовый файл ≤ 4 часа; ручных правок ≤ 30% кадров; себестоимость ≤ $25; слепая оценка 4 людьми ≥ 3.5/5; повторяемость — второй ролик делается без правок кода.

Если после пилота себестоимость выше $25 или правок больше половины — расширять на ТВ и Лувр нельзя, надо менять модели.

## 8. Риски

1. **Лицензии моделей.** «Open-weight» ≠ «можно всё»: у части весов запрет на коммерческое использование и на обучение других моделей. Проверять каждую карточку, фиксировать в `ai_models.license`.
2. **Права на обучающие данные.** LoRA на чужих видео/лицах/логотипах — прямой риск претензий. Свой материал или явная лицензия.
3. **Голоса и лица.** Клонирование голоса диктора требует письменного согласия; дипфейки — запрещены правилами магазинов и несут репутационный риск.
4. **Стоимость.** Петля 24/7 без лимита бюджета = счёт на тысячи долларов за сутки. Бюджет на задание и на сутки — обязательное поле, а не «потом».
5. **Хрупкость computer-use агентов.** Любое обновление чужого интерфейса ломает пайплайн. Детерминированные шаги (ffmpeg, шаблоны) надёжнее.
6. **Публикация без ревью.** Один плохой кадр в официальном канале WUN дороже, чем неделя ручной приёмки.
7. **Зависимость от одного провайдера.** Интерфейс адаптеров — не бюрократия, а страховка.

## 10. Решения, которые нужны от заказчика

1. Бюджет на пилот: сколько долларов на GPU/API мы готовы потратить до первого результата (предлагаю $300–500).
2. Провайдер инференса: своя аренда (RunPod/Vast) или managed (Replicate/fal). Для пилота — managed, для объёма — своя аренда.
3. Кто утверждает контент перед публикацией (имя роли, не «кто-нибудь»).
4. Юридический статус NFT-патентов и токенизации контента — до, а не после.
5. Первый канал: реклама для WUN или контент для Лувра. Одновременно — нет.

Пока нет ответов на 1 и 2, код писать можно и полезно (каркас и мок-пайплайн денег не тратят), а вот закупать GPU — нет.
