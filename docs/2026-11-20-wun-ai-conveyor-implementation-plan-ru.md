# План реализации: WUN AI-Конвейер

Дата: 2026-11-20. Статус: рабочий план, код не начат.
Связанные документы: `2026-11-20-wun-ai-conveyor-plan.md` (разбор и архитектура),
`2026-11-20-wun-ai-conveyor-estimate-ru.md` (часы и деньги).

Задача этого файла — превратить смету в задачи: что делаем, в каком порядке, чем
заканчивается каждый шаг и как понять, что он действительно сделан.

---

## 1. Пять правил, на которых держится вся сборка

1. **Сначала каркас, потом модели.** Весь путь «бриф → готовый файл» гоняется на моках,
   которые возвращают заглушки за 2 секунды. Если пайплайн работает на моках, подключение
   реальной модели — это новый файл адаптера, а не переписывание.
2. **Каждый шаг идемпотентен.** Повторный запуск стадии не создаёт второй артефакт и не
   списывает деньги второй раз. Ключ идемпотентности — `job_id + stage + attempt`.
3. **Бюджет — это поле в базе, а не настройка в голове.** У задания есть `budget_usd` и
   `spent_usd`. Достигли лимита — задание встаёт в `failed` с причиной `budget_exceeded`.
4. **Модели — сменные детали.** Между стадией и провайдером всегда адаптер
   (`VideoProvider`, `ImageProvider`, `TtsProvider`, `MusicProvider`, `LlmProvider`).
   Стадия не знает, кто именно рисует кадр.
5. **Человек только на приёмке.** Всё, что можно сделать детерминированно (склейка, титры,
   громкость, проверка длины), делает код. Человек смотрит и говорит «да» или «переделать».

## 2. Структура репозитория

```
apps/
  web/                  React 18 + Vite + TS + Tailwind + shadcn — экран приёмки /studio
  api/                  Fastify + TS — REST, вебхуки провайдеров, выдача задач воркерам
workers/
  ts/                   стадии без GPU: script, storyboard (промпты), qc, publish
  gpu/                  Python: shots (видео), audio (TTS + музыка), assembly (ffmpeg)
packages/
  shared/               типы, схема задания, состояния, расчёт стоимости
  adapters/             VideoProvider, ImageProvider, TtsProvider, MusicProvider, LlmProvider
  db/                   миграции, клиент, запросы с лейзами
infra/
  docker-compose.yml    Postgres + api + workers + MinIO (S3) локально
  Dockerfile.api
  Dockerfile.worker
docs/                   бриф, план, смета, этот файл
```

Почему монорепозиторий: стадии, адаптеры и типы меняются вместе. Разносить по разным
репозиториям на старте — это лишние версии и лишние релизы на каждую правку контракта.

## 3. Стек: что берём и почему

| Слой | Выбор | Почему так, а не иначе |
| --- | --- | --- |
| Оркестратор | Postgres-очередь + `FOR UPDATE SKIP LOCKED`, диспетчер на `node-cron` | На пилоте это 1–5 заданий в час. Redis, Kafka и Temporal — оверинжиниринг, у них своя цена в обслуживании |
| API | Fastify + TypeScript, Zod на входе | Тот же язык, что веб и WUN; быстрее Express, схемы проверяются на границе |
| Воркеры без GPU | Node + TS, общие типы с API | Один язык на всю бизнес-логику |
| Воркеры с GPU | Python 3.11 + ComfyUI (или API провайдера) | Все видеомодели и их экосистема — Python |
| Монтаж | ffmpeg, шаблоны фильтров в коде | Детерминированно, бесплатно, повторяемо; никакого computer-use |
| Хранилище | S3-совместимое: MinIO локально, R2/S3 в проде | Supabase Storage в WUN тоже S3-совместим, переезд — смена эндпоинта |
| База | Postgres 16 | Очередь, метаданные, стоимость — в одном месте |
| Веб | React 18 + Vite + TS + Tailwind + shadcn + TanStack Query | Совпадает с WUN, компоненты и привычки переносятся |
| Наблюдаемость | Структурные логи (pino) + таблица расходов + Sentry | Сначала надо видеть, сколько стоит каждый шаг, остальное потом |
| CI | GitHub Actions: lint, typecheck, unit, e2e на моках | Без зелёного CI не мержим |
| Локальный запуск | `docker compose up` | Один человек поднимает всё за минуту, без установок |

Отдельно: **свой Postgres, а не Supabase, внутри конвейера.** Конвейер — сервис с
долгими задачами и своими миграциями. С WUN он общается по API (авторизация, кошелёк,
публикация). Так чужая миграция не ломает очередь, а очередь не грузит прод-базу WUN.

## 4. Данные (8 таблиц, как в техническом плане)

`ai_briefs`, `ai_jobs`, `ai_job_steps`, `ai_artifacts`, `ai_models`, `ai_publications`,
`ai_costs` — плюс `ai_leases` для явных лейзов воркеров, если `locked_until` начнёт
не хватать.

Ключевые инварианты, которые проверяются тестами:

- `spent_usd <= budget_usd` всегда, иначе шаг не стартует;
- переход состояния только по таблице разрешённых (`machine.ts`), «из failed в approved» нельзя;
- у каждого артефакта есть `step_id`, `cost_usd` и `meta.model` — иначе себестоимость не считается;
- повторный запуск шага с тем же ключом идемпотентности возвращает существующий артефакт.

## 5. Этапы, задачи, часы

Идентификаторы задач (`P1.1`, `K2.3` …) нужны, чтобы ссылаться на них в коммитах и в
трекере. Часы сходятся со сметой: 40 + 140 + 160 + 120 + 120 + 60 = 640.

### M1. Ручной пилот — 40 ч, 1 неделя

Цель: честно узнать цену и время одного ролика. Кода в репозитории нет, только отчёт.

| ID | Задача | Ч | Зависит |
| --- | --- | --- | --- |
| P1.1 | Арендовать GPU (RunPod/Vast), поднять ComfyUI, проверить доступ | 4 | — |
| P1.2 | Прогнать 2 видеомодели и 1 модель картинок, замерить время и качество | 8 | P1.1 |
| P1.3 | Бриф + сценарий на 30 секунд + раскадровка из 6 кадров | 4 | — |
| P1.4 | Сгенерировать шоты, по 3 попытки на кадр, отобрать лучшие | 8 | P1.2, P1.3 |
| P1.5 | Озвучка (TTS) и музыка 30 секунд, подгонка по длине | 3 | P1.3 |
| P1.6 | Сборка в ffmpeg: склейка, титры, субтитры, громкость | 5 | P1.4, P1.5 |
| P1.7 | Замерить фактическую себестоимость и время, отчёт в `docs/` | 4 | P1.6 |
| P1.8 | Слепая оценка 4 людьми, решение go/no-go | 4 | P1.7 |

**Готово, когда:** есть файл 30 сек 1080p, отчёт с реальными цифрами (часы, доллары,
число переделок) и записанное решение — идём дальше или меняем модели.

**Стоп-условие:** себестоимость выше $25 или переделано больше половины кадров — дальше
не идём, пока не найдена другая модель.

## 6. Что делаем в первые две недели

1. День 1–2: `K2.1` + `K2.2` — репозиторий поднимается одной командой, миграции накатываются.
2. День 3–4: `K2.3` — состояния и переходы, тесты зелёные.
3. День 5–7: `K2.4` + `K2.5` — задание идёт по стадиям, лейзы не дают двум воркерам взять одно.
4. День 8–9: `K2.6` + `K2.7` — моки и склад артефактов.
5. День 10–14: `K2.8` + `K2.9` — экран приёмки и сквозной тест.

К концу второй недели есть работающий стенд, который ничего не стоит и который можно
показать. Реальные модели подключаются после этого — по одной, начиная с картинок.

---

## 7. Чего сейчас не делаем

- Kubernetes, Kafka, Temporal, микросервисы на каждую стадию — это для нагрузки, которой нет.
- Агент с управлением мышью и кликами по чужому интерфейсу — только если шаблонов ffmpeg не хватит.
- Своя GPU-ферма и покупка железа — только после 6–7 роликов в месяц стабильного спроса.
- Автоматическая публикация без человека — только после 30 принятых роликов подряд.
- Мобильное приложение для студии — экрана приёмки в вебе достаточно.
- Мультиязычность и автоматический дубляж — после того, как русский пайплайн стабилен.

## 8. Как понять, что этап действительно закрыт

Общий чек-лист на каждый этап:

- [ ] работает на чистой машине по инструкции из README, без «а у меня локально»;
- [ ] тест в CI падает, если сломать инвариант (проверяли намеренно);
- [ ] стоимость шага видна в базе и совпадает со счётом провайдера;
- [ ] повторный запуск не создаёт дублей и не списывает деньги второй раз;
- [ ] лимит бюджета останавливает задание, а не «предупреждает в логе»;
- [ ] отчёт по этапу лежит в `docs/` с реальными цифрами, а не с ожидаемыми.

## 9. Как перенести это в Linear, когда дойдёт

Документ уже размечен под импорт:

- этап (`M1`…`M6`) → **проект** в Linear;
- задача (`P1.1`, `K2.3` …) → **issue**, часы → оценка, `Зависит` → блокирующая связь;
- недели этапов → **cycles**, по одному на этап;
- `Готово, когда` каждого этапа → описание проекта и его definition of done;
- первый спринт (раздел 6) → первый cycle, остальное в бэклоге.

Ссылки на задачи в коммитах (`K2.4: диспетчер очереди`) дадут автозакрытие при подключении
GitHub-интеграции Linear.

## 10. Решения, которые нужны до кода

1. Бюджет на пилот в долларах: предлагаю $300–500 на аренду GPU и API.
2. Провайдер: managed (Replicate/fal) на пилот или своя аренда (RunPod/Vast) сразу.
3. Кто принимает контент — конкретное имя, а не «кто-нибудь».
4. Первый канал: реклама для WUN или контент для Лувра. Одновременно не начинаем.
5. Нужны ли закрывающие документы от российского юрлица — от этого зависит, где арендовать GPU.

Ответы на 1 и 2 нужны только к моменту M1. Каркас M2 пишется без них и денег не тратит.
